# Provider & Integration Decisions

## ADR-001: Job Sources — Remotive and Arbeitnow

**Date**: 2026-10-10  
**Status**: Accepted

### Context
The prompt requires at least two job sources with verified terms, free access, and no multi-user aggregation prohibition.

### Evaluated Providers

| Provider | Auth | Free Tier | Multi-User Permitted | Attribution | Data Delay | Notes |
|----------|------|-----------|---------------------|-------------|------------|-------|
| **Remotive** | None | Yes | Yes (fair use) | Required (link to job URL + credit Remotive) | 24 hours | Max 4 fetches/day recommended; 2/min hard limit |
| **Arbeitnow** | None | Yes | Implied (no prohibition) | Required (link to arbeitnow.com) | None stated | "As is"; access revocable at any time |
| Adzuna | app_id + app_key | 2,500/month | **Prohibited** without written agreement | Required | None | Commercial aggregation requires license after 14-day trial |
| JSearch (RapidAPI) | API key | 200 req/month | Unclear; RapidAPI ToS applies | N/A | None | 200 req/month is insufficient for multi-user |

### Decision
**Primary**: Remotive API (`https://remotive.com/api/remote-jobs`)  
**Secondary**: Arbeitnow API (`https://www.arbeitnow.com/api/job-board-api`)

### Risks & Mitigations
- Remotive data is delayed 24 hours → documented in search results metadata
- Arbeitnow access is revocable → implement graceful degradation; one provider failure does not block the other
- Both are remote/international focused → limitation documented; not suitable for region-specific in-person roles without additional providers
- Attribution requirement → enforced in `JobRecord.attribution` field and communicated to frontend via API contract

### Caching Policy
- Remotive: cache fetched batch for up to 6 hours; never re-fetch more than 4 times/day per provider
- Arbeitnow: cache for up to 1 hour; implement circuit breaker if >3 consecutive failures

## ADR-002: LLM Provider — Google Gemini Flash

**Date**: 2026-10-10  
**Status**: Accepted (provisionally, pending Phase 0 API verification)

### Context
Need an LLM for: profile extraction from resume text, job matching explanation generation, resume tailoring, and claim validation support. The interface must be provider-independent so it can be swapped.

### Evaluated Providers

| Provider | Free Tier | Req/Day | Privacy | Structured Output | SDK Status |
|----------|-----------|---------|---------|-------------------|------------|
| **Gemini Flash 1.5** | Yes | 1,500 | Data may be used for training (free tier) | Yes (JSON mode) | Stable |
| Groq (Llama) | Yes | ~14,400 | Better privacy claims | Yes | Stable |
| OpenAI | No free tier | — | Paid | Yes | Stable |
| Ollama (local) | Yes (self-hosted) | Unlimited | Full privacy | Yes | Stable |

### Decision
**Default**: Gemini Flash 1.5 via `google-generativeai` SDK, behind a `LLMAdapter` protocol interface.  
**Alternate (configurable)**: Groq via `SCOUT_LLM_PROVIDER=groq` env var for better privacy or higher limits.

### Interface Contract
All LLM calls go through `providers/llm/base.py`:
```python
class LLMAdapter(Protocol):
    async def extract_structured(self, prompt: str, schema: type[BaseModel]) -> BaseModel: ...
```
This ensures:
- Schema-validated output on every call
- Provider can be swapped without changing business logic
- Rate limit handling is centralized

### Privacy Concern (Documented)
On the Gemini free tier, Google may use inputs for model improvement. Full resume text **must not** be sent to the LLM tracing provider (Opik/equivalent) by default. Furthermore, consider sending only structured extracted fields (not raw resume text) to the LLM in privacy-sensitive deployments. Document this limitation to users at registration.

### UNVERIFIED
The exact Gemini Flash 1.5 free-tier limits (1,500 req/day) should be verified in Phase 1 against the current AI Studio quota page before implementation depends on them.

## ADR-003: Database & Auth — Supabase

**Date**: 2026-10-10  
**Status**: Accepted with documented limitations

### Free Tier Constraints (Verified)
- 500 MB database
- 1 GB storage (50 MB max per file)
- 50,000 MAU
- Project pauses after 1 week idle → **mitigation**: use an external uptime monitor (free tier of UptimeRobot) to ping the health endpoint and prevent pausing
- No automatic backups → **mitigation**: manual pg_dump schedule documented in runbook; recommend Pro tier before any user data is critical
- Shared compute (512 MB RAM)

### Decision
Accept Supabase for the beta phase. RLS policies are implemented as defense-in-depth. Ownership checks in application code are the primary authorization mechanism (using service role key server-side only).

### Migration Plan
If Supabase changes terms or performance is unacceptable:
1. Replace supabase-py with asyncpg/psycopg3
2. Replace Supabase Auth with a self-hosted JWT issuer (e.g., custom PKCE flow)
3. Replace Supabase Storage with S3-compatible provider (Cloudflare R2 free tier: 10 GB)
4. All SQL migrations are standard PostgreSQL; no Supabase-specific extensions used

## ADR-004: Background Task Queue — PostgreSQL SKIP LOCKED

**Date**: 2026-10-10  
**Status**: Accepted

### Context
Long-running operations (job search ~30-90 s, resume generation ~20-60 s) must not depend on an open HTTP connection.

### Evaluated Options
| Option | Cost | Durability | Complexity | Free Tier |
|--------|------|------------|------------|-----------|
| **PostgreSQL SKIP LOCKED** | $0 | High | Low | Yes |
| Redis + RQ | $0 (Upstash free) | Medium | Medium | Limited (10K commands/day) |
| Celery + broker | $0 (with Redis) | High | High | Depends |
| asyncio background tasks | $0 | Low (no persistence) | Low | Yes |

### Decision
PostgreSQL-backed task queue using `SELECT FOR UPDATE SKIP LOCKED`. The `tasks` table stores task type, owner, status, retry count, and sanitized error. The worker polls every 5 seconds (configurable).

**Rationale**: No extra infrastructure; durable across restarts; idempotency enforced by unique constraint on task inputs; retry limit prevents runaway loops.

**Beta deployment**: Worker runs as an asyncio task within the same Uvicorn process. Phase 8 moves it to a dedicated worker when Render's background worker (paid) or an alternative free option is evaluated.

## ADR-005: PDF Rendering — weasyprint (HTML-to-PDF)

**Date**: 2026-10-10  
**Status**: Accepted (pending install verification)

### Decision
Generate structured resume data (Pydantic model), render to HTML via Jinja2 templates, convert to PDF via weasyprint.

**Rationale**: 
- No external service dependency (offline, no API quota)
- Template-controlled output (no arbitrary HTML injection)
- Active maintenance; BSD license
- Produces accessible, text-based PDFs (pdfminer can extract text for verification)

**Alternative**: fpdf2 (as used in reference repo) if weasyprint system dependencies are too complex in containerized deployment. Will evaluate in Phase 6.

## ADR-006: Observability — structlog + Request IDs

**Date**: 2026-10-10  
**Status**: Accepted

### Decision
- **Structured logging**: `structlog` with JSON output
- **Request correlation**: UUID request ID in every log line and every HTTP response header (`X-Request-ID`)
- **LLM tracing**: Optional; uses `OPIK_API_KEY` env var; **disabled by default**; when enabled, only structured metadata (not raw prompts) is sent
- **Metrics**: Prometheus metrics endpoint (`/metrics`) for operational visibility; covered by basic Render monitoring

### Privacy Rules (Non-Negotiable)
Never log:
- Raw resume text or any PII
- Auth tokens or JWTs
- LLM prompts containing personal data
- Supabase keys or any secrets
- Full job description text (log job ID only)

## ADR-007: Deployment (Beta) — Render.com Free Tier

**Date**: 2026-10-10  
**Status**: Accepted with documented limitations

### Known Limitations (Documented)
- Spins down after 15 minutes idle → cold start 30-60 s
- 0.1 CPU, 512 MB RAM → limits concurrency
- No persistent local filesystem → all files to Supabase Storage
- No separate background worker on free tier → worker runs in-process initially
- 750 instance hours/month → sufficient for one always-on service

### Mitigation
- Use UptimeRobot (free) to ping `/api/v1/health` every 5 minutes to prevent spin-down
- Queue-backed tasks survive spin-down (tasks persist in PostgreSQL)
- Phase 8 evaluates: Railway.app, Koyeb, or self-hosted VPS for dedicated worker

### Migration Path
The application has no Render-specific code. Moving to a different host requires only updating environment variables and the Procfile/Dockerfile.
